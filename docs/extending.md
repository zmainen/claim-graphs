# Extending the machinery

How to add a capability so that it is declared, runnable, recorded and gated — rather than
described. The test of whether something belongs in this repository is not whether it is useful
but whether it can be *run and checked*: a capability that exists only as advice drifts from
everything around it, silently, and the first evidence is a wrong graph.

This document is the general procedure. `docs/design/` holds the reasoning for individual
decisions; `pipeline/layers.yaml` is the declaration everything below writes to.

## 1. Decide whether it is a layer

A **layer** is a node in the processing graph: it asks one question of declared inputs and
produces a new version of something. If a capability takes inputs that already exist, produces
an artifact, and could be re-run, it is a layer, and making it one buys the ledger, staleness,
the agent-mode loop and a place in the state matrix for nothing.

Things that are not layers, and why:

| Not a layer | Because |
|:--|:--|
| `contract`, `skill` | they produce *inputs* to layers, from declarations |
| `evaluate` | it asks about the prompts, not about a document, and nothing consumes it |
| approval | it is an operation on a *version* a layer produced, not a step |

Approval deserves the emphasis. Review is not a layer: a person reads what a layer produced and
approves *that version*, and when the layer runs again the approval does not follow, because it
was granted to text that no longer exists.

## 2. Declare it

Add an entry to `pipeline/layers.yaml`. The fields are documented at the top of that file; these
are the ones that carry weight.

```yaml
  - id: spec-paper
    group: induction
    kind: step                 # step | candidate | judgement | feature | question
    scope: paper               # paper | corpus
    title: Paper spec
    question: What argument would this paper have to make, and what would have to be true?
    how: >
      What it is given, what it returns, and what it gets wrong. `question` says why the layer
      exists; this says how it answers. Rendered on the layer page.
    needs: [claim-format, questions]        # staleness flows along these
    reads: [extract/prompts/spec-paper.md,  # inputs that are not another layer's output
            extract/prompts/contract/vocabulary.md]
    produces: ["runs/{paper}/spec-paper.output.json"]
    command: "cd extract && python3 -m claim_graphs.cli spec-paper --paper {paper}"
    by_from: model             # the key in the first produced file naming who answered
    doc: /docs/layers/#spec-paper
```

`reads` is the field that does the work people forget. Every path listed there is hashed into
the run record, so editing a prompt marks every run that used it stale. A prompt left out of
`reads` can be rewritten under a graph that still reports itself current.

`by_from` is what makes the layer work in agent mode: the runner reads that key out of the
output into the ledger's `by`, because from outside the command all it could otherwise record
is that it invoked something.

## 3. Write the task, not the contract

A model-answered layer's prompt is two parts. The **task** — what this role reads and what to
look for — is written by hand at `extract/prompts/<layer>.md`. The **contract** — what a claim
is, what each role and relation means, the shape to return — is generated by `contract.py` from
`vocabulary.py`, `scripts/relations.py` and `schema.py`, and composed in by `prompts.py`.

Never restate a definition in a task file. If the task needs a definition the contract does not
carry, add it to the declaration and regenerate; that is what keeps every role, every export and
the agent-facing skill saying one thing.

Declare the rendered contract files your layer reads in `reads`, so a vocabulary change marks
its runs stale.

## 4. Add the runner

A subcommand in `extract/claim_graphs/cli.py` and a layer function in `layers.py`. Two
requirements, both of which the existing layers meet and neither of which is optional:

- **`--dump-prompt` and `--answer`.** Every model-answered layer must be able to emit the exact
  `(system, user)` it would send, and to accept a reply made elsewhere through the same
  validation a backend reply gets. This is the seam that makes agent mode and API mode the same
  process. `cli._dump` is three lines to call.
- **Output validated against a pydantic model in `schema.py`.** A layer that accepts free-form
  JSON has no contract, and the failure surfaces three layers downstream.

The backend is not your concern: who answers is chosen by profile and lives outside this
repository.

## 5. Gate it

Add a test under `extract/tests/` and a line to `make check`. The suite runs standalone as well
as under pytest — copy the `__main__` block from any existing test file. If the layer's prompt
reads contract files, `test_prompt_contract.py` already checks that the declaration, the
renderer and the prompt agree; add your layer to `LAYER_OF` there so it is covered.

If the capability teaches an agent anything, it also belongs in the skill — and in the skill's
*sources*, `docs/skill/`, never in the rendered output. A sequence an agent follows should be a
token rendered from the declaration (`{{agent-runbook}}` is the worked example), so that adding
your layer updates the instructions without anyone editing them.

## 6. Record why

A design note in `docs/design/<date>-<slug>.md` when the change is a decision rather than a
mechanism: what was considered, what was chosen, and what the choice costs. The layer's
`question` field is the one-line version; the note is the argument.

## Worked example: the forward workflows

`skills/claim-structures/workflows/spec-paper.md` and `design-experiment.md` describe the
forward direction — building the argument as a graph before the prose or the data exist. They
are the strongest claim the format makes, and today they have no layer, no declared prompt, no
ledger and no gate. Nothing exercises them, so nothing will notice when the schema moves under
them.

Both fit the model without strain:

- **`spec-paper`** reads a research question and a draft outline, and produces a claim set: the
  hypothesis, the rivals it must eliminate, the predictions each entails, and the empirical
  claims that would test them. The figure plan falls out of it — one panel per empirical claim.
- **`design-experiment`** reads a hypothesis and produces what has to be measured to discriminate
  it from its rivals: the predictions that differ between them, and the controls that eliminate
  each.

Neither produces claims about the world that a document asserts, so both need a `provenance`
that says as much: a claim authored forward, before the data, is not the same kind of object as
one induced from a published result, and the interchange form must not present them as
interchangeable.
